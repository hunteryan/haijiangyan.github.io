业务方向执行细则
2.0 源数据业务语义地图产出

目标：将技术元数据翻译为业务可理解的资产目录，解决数据信任问题。

标准动作：

  • 5维信息采集：对每个数据源强制采集技术表名/字段、业务中文名、所属业务域、支撑分析场景、数据Owner及联系方式。
  • L1-L3分级标注：按业务重要性分级，优先保障L1级（核心指标依赖）数据的语义完整性。
  • 双向验证签收：技术侧完成初版后，必须由业务Owner"认领+修正"签字，未确认数据禁止进入下游建模。
交付物：《数据源业务语义地图》、Owner签收记录、语义完整性检查报告
2.1 主题域划分

目标：建立不重叠、不遗漏、不交叉、可扩展的企业级业务数据边界，实现资产按域管理、指标按域归口、模型按域建设。

标准动作：

  • 梳理企业全业务链路，输出业务流程地图。
  • 按业务链路法输出一级主题域。
  • 按业务过程拆解二级子域。
  • 把所有源系统、数据表、指标一一归属到对应域。
  • 业务Owner评审确认，解决边界交叉问题。
  • 发布最终版主题域清单与边界定义。

核心划分方法：

业务链路法 系统归属法 指标归口法 不交叉原则 两级结构法 Owner确权法
  • 业务链路法：按照企业真实业务发生流程从上到下梳理，形成天然业务边界。
  • 系统归属法：按照源业务系统天然边界归类，确保一个系统优先归属一个主题域。
  • 指标归口法：把高频指标、核心报表按业务口径归属到对应域，确保指标有唯一归属。
  • 不交叉原则：一个表/一个字段/一个指标只属于一个主题域，禁止跨域重复定义。
  • 两级结构法：一级域 = 业务大类，二级子域 = 业务过程/模块，确保结构稳定、可扩展。
  • Owner确权法：每个主题域必须指定业务Owner + 数据Owner，权责唯一。
交付物：《业务主题域划分手册》
2.2 历史脚本逆向提炼高频指标 + 业务补充

目标：从存量混乱资产中萃取共识，避免推倒重来，同时防止技术债延续。

标准动作：

  • 自动化聚类：SQL解析历史脚本，提取高频GROUP BY维度与聚合函数，生成"事实指标热度榜"。
  • 差异归类预案：将同一业务概念的不同计算逻辑归类，提前准备统一/并存/废弃3种处理预案。
  • 三轮对齐闭环：展示热度榜→数据对比辅助决策→签订《指标定义契约》。
  • 缺口识别纳入：同步收集"想要但没有"的新需求，纳入首期建设优先级矩阵。
交付物：《历史指标热度分析报告》、《核心指标定义契约》、新增需求优先级矩阵
技术方向执行细则
3.1 分层架构设定

原则：以业务查询模式驱动，而非理论套用。

标准动作：

  • 基于历史查询统计80%高频粒度与关联复杂度，决定DWS预聚合粒度。
  • 明确定义每层输入输出约束并写入规范。
  • 预设临时层/沙箱层容纳探索性需求。
交付物：《分层架构决策记录》、层级边界检查清单
3.2 拆解源数据字段生成统一新词根

原则：从人工约定到机器强制执行。

标准动作：

  • 逆向萃取历史高频字段 + 正向映射业务术语，形成《标准词根库V1.0》。
  • 开发DDL校验插件集成至CI流水线，不合规直接阻断。
  • 设置例外审批留痕机制。
交付物：标准词根库、CI校验插件、例外审批台账
3.3 模型设计规范

原则：让正确的事容易做，错误的事难发生。

标准动作：

  • 提供标准化建表DDL模板（含注释/分区/生命周期）。
  • 模型变更必须附带血缘影响分析。
  • 大表强制设计排序键/分桶策略并提供性能基线评估。
交付物：建模DDL模板、模型评审Checklist、性能基线评估表
3.4 开发规范

原则：规范不应是负担，而应是提效工具。

标准动作：

  • 提供AI辅助生成Prompt模板。
  • 沉淀公共函数库，禁止重复造轮子。
  • 集成SQL Linter自动化处理格式规范。
交付物：AI Prompt模板库、公共函数库、Linter配置文件
3.5 校验规则

原则：质量保障左移至开发态。

标准动作：

  • 规则以YAML/JSON配置嵌入ETL任务，与代码同版本管理。
  • 建立分级熔断机制（强规则阻断 / 弱规则告警）。
  • 提供测试数据构造工具支持本地验证。
交付物：质量规则配置库、熔断策略矩阵、测试数据生成器
